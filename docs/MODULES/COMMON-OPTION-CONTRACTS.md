# WPEssential — Common Option Contracts

Status: **Phase 0 shared detailed specification**

These contracts apply to every module unless that module's detailed spec explicitly overrides them. They resolve repeated option behavior so individual module specs do not duplicate the same validation/default rules.

## 1. Definition identity

### `id`
- immutable UUID generated by WPEssential;
- never reused after deletion;
- used for internal references/import mapping;
- not user-editable.

### `name` / `title`
- human-readable string;
- required for user-created definitions unless WordPress native object semantics require otherwise;
- trimmed;
- blank after trimming is invalid;
- UI recommended maximum 120 characters unless module requires shorter;
- HTML not allowed in identity labels.

### `key` / `slug`
- machine-readable string;
- generated from name when possible;
- lowercase/sanitized according to target API;
- uniqueness scope declared by module;
- changing after references exist shows impact preview;
- immutable by default for definitions with external/API references unless migration path is explicit.

### `description`
- optional;
- plain text or sanitized rich text according to module;
- not used as authorization logic.

### `internal_notes`
- optional admin-only text;
- never exposed via generic renderer/token/API;
- excluded from public export unless export type explicitly includes administrative notes.

## 2. Definition lifecycle

Default configurable-definition states:
- Draft
- Active
- Disabled
- Archived

### Draft
- stored/revisioned;
- has no runtime effect unless preview explicitly requests draft.

### Active
- participates in runtime behavior.

### Disabled
- definition remains editable but runtime effect is off, except modules where disabling enforcement could create a security exposure; those modules define a safe enforcement mode explicitly.

### Archived
- no new normal use/selection;
- historical references preserved;
- deletion requires dependency resolution.

Delete is not a normal lifecycle state. Delete is a destructive action with impact analysis.

## 3. Save behavior

- client-side validation improves UX but server-side validation is authoritative;
- REST/admin request rejects unknown privileged fields rather than silently mass-assigning;
- save returns normalized representation and revision ID;
- optimistic UI may be used only after server response confirms mutation;
- dirty-state warning on navigation away from unsaved changes;
- concurrent updates use version/revision precondition where practical and show conflict UI instead of silently overwriting.

## 4. Common list behavior

Default page size: **25**.

Optional sizes: 25 / 50 / 100. Larger values require module-specific justification.

Every list that can grow large uses server-side pagination.

Common list controls where meaningful:
- search;
- status filter;
- source/owner filter;
- sort;
- page size;
- column visibility;
- bulk selection;
- saved view only where repeated operational value exists.

Search input:
- debounced client request;
- server-side bounded query;
- no wildcard/raw SQL interpolation;
- clear/reset control.

URL query state should preserve meaningful filters/sort/page for deep-linking without putting secrets or PII into URLs.

## 5. Common row actions

Standard non-destructive actions:
- View
- Edit
- Duplicate
- Dependencies / Used By
- Export
- Audit / History

Standard lifecycle actions:
- Enable/Activate
- Disable/Pause
- Archive
- Restore from Archive

Delete:
- absent when object cannot safely be deleted;
- otherwise dependency preview + capability + nonce + confirmation;
- typed confirmation or reauthentication for high-impact deletion;
- audit event;
- background execution if large.

## 6. Common filters

Boolean filters use All / Yes / No rather than ambiguous unchecked states.

Multi-select filters:
- OR within one filter group unless explicitly labeled otherwise;
- AND/OR across groups follows module/query semantics;
- active selections rendered as removable chips where useful.

Date range:
- site timezone by default;
- inclusive start;
- end semantics explicitly shown;
- absolute timestamps stored in UTC where WordPress/runtime convention supports it.

## 7. Confirmation levels

### Level 0 — no confirmation
Read-only operations and reversible low-risk UI changes.

### Level 1 — simple confirmation
Archive, disable, unlink, remove non-destructive association.

### Level 2 — typed confirmation
Deleting definitions with dependents, bulk destructive changes, reset operations.

### Level 3 — reauthentication + typed confirmation + restore point
Database destructive mode, site reset, security-sensitive dangerous action, permanent data deletion where recovery matters.

Module may raise but not lower the required level without security review.

## 8. Capabilities

Each module receives distinct capabilities for at least:
- read module;
- manage definitions;
- manage runtime records where different;
- run/execute where relevant;
- import;
- export;
- diagnostics;
- dangerous operations if applicable.

List/read/edit/delete checks are server-side. A visible menu or React route never grants access.

Object-level authorization is required where records belong to users, memberships, conversations, entries, tickets or other scoped principals.

## 9. Conditional UI

An option hidden because another option disables it:
- remains in persisted configuration only if preserving it is safe and useful;
- is ignored by runtime while inactive;
- UI indicates when re-enabling restores previous sub-settings where that behavior exists.

A disabled control must provide a reason when the reason is not obvious.

## 10. Validation response

Field validation returns:
- stable machine error code;
- field path/key;
- safe human message;
- optional remediation metadata.

Never expose stack traces, raw SQL, filesystem secrets or provider credentials to end users.

## 11. Secrets

Secret inputs:
- store Vault reference, not plaintext in ordinary definition JSON;
- masked after save;
- replacement is write-only by default;
- reveal requires separate capability and reauthentication only if reveal is supported at all;
- never returned in generic REST/Ability/list endpoints;
- excluded from config export;
- audit records secret changed, not secret value.

## 12. PII classification

Fields/records that may contain PII declare:
- purpose;
- visibility;
- export permission;
- retention;
- deletion/anonymization behavior;
- logging redaction.

Do not collect IP, user agent, full request bodies or external payloads by default unless operational/security purpose is documented.

## 13. Revisions

Configuration definitions:
- revision created on meaningful save;
- store actor/time/schema version/change summary;
- diff view;
- restore creates a new revision rather than deleting history;
- secret values redacted from diffs;
- excessive auto-save revisions may be compacted according to retention policy.

Runtime records such as messages/form entries are not automatically treated as configuration revisions.

## 14. Import/export

Every definition export includes:
- object type;
- stable UUID;
- schema version;
- module version requirements;
- dependencies;
- normalized configuration;
- checksum/package metadata where packaged.

Default exclusions:
- secrets;
- access tokens;
- transient caches;
- operational logs;
- unnecessary PII.

Import always validates before mutation. Cross-site IDs use UUID/resource mapping rather than trusting numeric WordPress IDs.

## 15. Dependencies

Dependency types:
- hard: cannot operate without target;
- soft: feature degrades but definition remains valid;
- runtime: dependency needed only when executing/rendering;
- external integration: provider/plugin dependency.

Deleting a referenced definition:
- hard dependency blocks;
- soft dependency prompts detach/degrade choice;
- bulk cascade deletion is not offered casually.

## 16. Pro entitlement state

When WPEssential Pro entitlement expires:
- data stays local;
- configuration readable/exportable;
- safe deployed rendering/enforcement continues where stopping would break/expose the site;
- creation/editing may become read-only;
- mutating background operations may pause according to module policy;
- UI shows exact entitlement reason and upgrade/renew action;
- no module may invent a different licensing behavior without ADR.

## 17. Module enable/disable

On disable:
- optional assets/hooks stop loading;
- background schedules stop/pause safely;
- data is retained;
- dependencies show degraded state;
- security/access modules must define whether minimal enforcement remains active to avoid accidental exposure;
- uninstall data deletion is separate.

## 18. UI state defaults

All screens plan:
- skeleton/loading state;
- empty first-use state with primary action;
- no-results filtered state with clear filters;
- 403 state;
- request failure with retry where safe;
- dependency unavailable state;
- module disabled state;
- Pro missing/expired state;
- success toast/inline status;
- background progress state where applicable.

Notifications should not disappear before the user can reasonably perceive them, and critical errors persist until dismissed/resolved.

## 19. Accessibility

- semantic buttons/links/forms;
- visible focus;
- keyboard-operable menus/dialogs/drag-drop alternatives;
- labels and described-by text for inputs;
- status not communicated by color alone;
- dialog focus trap/return focus;
- error summary links to invalid fields for long forms;
- data tables expose headers appropriately;
- reduced-motion preference respected.

## 20. Responsive admin behavior

- no horizontal page overflow caused by ordinary forms;
- large tables may use controlled horizontal scrolling;
- primary actions remain reachable on narrow widths;
- side panels become drawers/stacked regions;
- drag/drop has non-drag alternative.

## 21. Asset loading

Every module declares exact admin screen IDs/routes and frontend render markers.

Default:
- module admin JS/CSS only on module screens;
- integration assets only on third-party screen when integration surface is present;
- frontend assets only if rendered component requires them;
- no global `admin_enqueue_scripts` bundle without screen guard;
- shared chunk loaded once.

## 22. Audit baseline

Audit mutations record:
- event name;
- actor principal;
- target type/UUID;
- site/network context;
- timestamp;
- source UI/API/Ability/CLI/job;
- correlation ID;
- safe before/after summary or diff reference;
- result;
- reason for privileged manual override when required.

## 23. Background work

Long-running actions:
- enqueue job instead of holding admin request;
- idempotent where possible;
- progress counters;
- retries bounded;
- cancellation semantics explicit;
- partial failure visible;
- correlation/run ID;
- final result retained for diagnostic period.

## 24. Default performance limits

Unless overridden:
- admin preview lists: 25 rows;
- public query page size: 20;
- maximum generic public page size: 100;
- remote request timeout target: 10s, adapter-specific override justified;
- remote response size bounded;
- bulk mutation batch size starts conservatively and is benchmarked before release;
- nested render/relation traversal depth must be bounded.

These are planning defaults, not claims of proven optimal values.

## 25. Diagnostics

Every module diagnostic surface should answer:
- enabled/healthy/degraded state;
- module/schema version;
- missing dependency;
- failed jobs;
- recent safe errors;
- data integrity check where meaningful;
- repair operation where safe;
- copy diagnostics with redaction.

## 26. Extension registration

Third-party extension points use registered PHP APIs/contracts during plugin bootstrap, not user-entered arbitrary class/function names.

Registrations declare:
- stable extension key;
- label/description;
- input/output schema;
- capability/policy implications;
- supported contexts;
- version compatibility.

## 27. Test inheritance

Every module inherits tests for:
- unauthorized screen/API access;
- CSRF/nonce failure;
- unknown field mass assignment;
- malformed UUID/key;
- create/edit/archive/delete lifecycle;
- disabled module;
- expired Pro state;
- import/export round trip;
- dependency deleted/disabled;
- asset isolation;
- accessibility of critical flows.

Module specs add risk-specific tests.
