# WPEssential — Content Model Detailed Specifications

Status: **Phase 0 — specified with open ADR/compatibility items**

Applies `COMMON-OPTION-CONTRACTS.md` and resolves the module-specific option inventory for CPT, Taxonomy, Custom Fields, Relations and Status.

---

# 1. Custom Post Types Builder — Free

## Ownership
WPEssential owns only CPT definitions created/imported into WPEssential. Core/plugin/theme registrations are discovered read-only unless a documented supported override adapter exists.

## Identity defaults and validation
- `plural_label`: required; default from entered name.
- `singular_label`: required; generated by user-facing wizard suggestion, never linguistically assumed as authoritative after save.
- `post_type_key`: required; sanitized with WordPress-compatible key rules; maximum must follow current `register_post_type()` constraints; reserved/core names blocked.
- `description`: optional plain text.

Changing a key after activation is treated as migration, not a normal rename.

## Labels
Default mode: **automatic labels on**. User may enable individual override.

Every WordPress-supported label exposed by current compatibility floor is stored as optional override. Empty override means use generated/default WordPress behavior rather than storing meaningless empty strings.

## Registration switches
Recommended creation defaults for a normal public content type:
- public: true
- publicly queryable: inherit public
- show UI: inherit public
- show in menu: inherit show UI
- show in admin bar: inherit show in menu
- show in nav menus: inherit public
- exclude from search: false
- hierarchical: false
- can export: true
- delete with user: false
- map meta cap: true when custom capability mapping is selected; otherwise WordPress default semantics

Every inherited setting has UI state `Inherit` rather than duplicating a derived boolean invisibly.

## Features/supports
Default: title + editor. Thumbnail is suggested, not forced.

Each support is a multi-select. Unsupported/version-dependent supports appear disabled with reason rather than being saved and ignored.

## Admin menu
- position: optional integer; blank lets WordPress choose.
- icon: default `dashicons-admin-post`; icon picker supports Dashicons and registered sanitized icon adapters.
- attaching arbitrary existing plugin menu requires compatibility warning; no menu manipulation outside supported WordPress registration args.

## Archive/rewrite
Default:
- has archive: false
- rewrite: true for public/queryable types
- rewrite slug: post type key
- with front: true
- feeds: inherit archive/public semantics
- pages: true

Changing slug/archive/rewrite shows affected permalink preview and schedules one rewrite flush after successful definition change.

## REST
Default show in REST: **true for new public CPTs**, because block editor/API interoperability is expected; user may disable.

- REST base blank = WordPress default.
- namespace blank = WordPress default.
- custom controller is not a text box; extensions must register selectable controller adapters.

## Capabilities
Modes:
1. WordPress default `post/posts` model.
2. Generated custom capability type.
3. Advanced explicit map.

Advanced map is collapsed behind warning. Capability changes show roles currently holding affected caps and can link to Role Manager when Pro exists.

## Taxonomies
Multi-select registered taxonomies. Creating new taxonomy launches Taxonomy Builder with returned UUID attached after save.

Detach changes registration only; it does not delete terms.

## Lifecycle
- Draft CPT definition does not register runtime type.
- Active registers at canonical hook priority decided by kernel.
- Disabled unregisters WPE-managed type while retaining definition; UI must warn that content remains in DB and may become inaccessible through normal admin routes.
- Archive behaves like Disabled plus hidden from default selectors.

## Delete
Delete definition only; underlying posts are not deleted unless a separately designed destructive content deletion flow is chosen. UI states this explicitly.

## Diagnostics
- key collision
- rewrite collision
- registration overridden by another plugin
- missing capability mapping
- REST route collision
- attached taxonomy missing
- content count for inactive definition

## Risk tests
- reserved key rejection
- activation with existing posts
- rewrite change
- external CPT remains unmodified
- disabled CPT content preserved
- REST on/off
- capability lockout regression

# 2. Taxonomy Builder — Free

## Identity
- singular/plural required.
- taxonomy key required, sanitized, unique, reserved names blocked.
- key change is migration-impacting.

## Labels
Automatic labels default on with per-label overrides, same contract as CPT.

## Behavior defaults
For a normal public taxonomy:
- hierarchical: false
- public: true
- publicly queryable: inherit public
- show UI: inherit public
- show in menu: inherit show UI
- show in nav menus: inherit public
- show tag cloud: inherit show UI
- show in quick edit: inherit show UI
- show admin column: false
- sort: false

`show_admin_column` can be quick-enabled, but Admin Columns Builder remains the richer column solution.

## Object types
At least one object type recommended but not mandatory for draft. Activation with no object type allowed only after warning because taxonomy would not be practically usable.

External/discovered object types stored by stable key and checked on runtime; missing object type produces degraded diagnostic, not fatal error.

## Rewrite/query
- query var: true/inherit by default when public.
- rewrite: true when public.
- slug: taxonomy key.
- hierarchical rewrite follows hierarchical=false by default.
- with front true.

## REST
Default true for newly created public taxonomy. Base/namespace blank inherit WordPress defaults. Controller adapters only through extension registry.

## Capabilities
Default uses standard term capabilities. Advanced fields expose manage/edit/delete/assign terms with capability existence warnings.

## Default term
Disabled by default. When enabled:
- select existing or define name/slug/description;
- creation occurs idempotently during activation/migration;
- failure produces diagnostic, does not repeatedly create duplicates.

## Delete/lifecycle
Deleting definition never deletes terms or term relationships automatically. Separate cleanup action may be designed later with impact preview.

## Diagnostics/tests
- reserved/colliding key
- rewrite collision
- missing object type
- term data persists on disable/delete definition
- capability mapping
- REST behavior

# 3. Custom Fields Builder — Pro

## Storage ownership
Field definition does not automatically own all values. Storage adapter owns persistence semantics. Deleting a field definition defaults to **retain stored values**, with optional later cleanup job explicitly selected.

## Field group defaults
- status Draft until first explicit Publish.
- title required.
- key generated immutable after external references exist.
- presentation style: Standard.
- label placement: top.
- instruction placement: below label.
- order: 0/automatic.

## Location rules
Rule UI: groups of AND conditions, groups OR-ed together, matching ACF-like mental model but implemented through Conditions Registry.

Every location matcher declares operand types and supported operators. No free-text executable condition.

Default first location for a new group: user selects explicitly; no accidental “all posts”.

## Common field contract
- key immutable UUID + machine name unique within group.
- `required`: false.
- `default`: null/empty appropriate to type.
- `read_only`: false.
- `disabled`: false.
- REST exposure: false by default for sensitive/unclassified fields; public safe fields may be opt-in.
- Ability exposure follows Data Source policy, not independent bypass.

## Text / textarea
- value normalized to string.
- min/max optional non-negative ints, min <= max.
- regex pattern expert option; validate regex before save and impose runtime complexity safeguards.
- text field HTML stripped; textarea stores plain text unless explicitly rich-text type.

## Email/URL/tel
- email uses WordPress/email validation and normalized safe string.
- URL uses validated URL; allowed schemes default http/https.
- tel stored string, not numeric, because formatting/leading `+` matter.

## Number/range
- numeric type selection integer/decimal.
- step default 1 for integer, `any`/sensible precision for decimal according to schema.
- min/max optional.
- locale display separate from canonical stored numeric value.

## Password/secret
Password-like ordinary user password is never stored by this field. `Secret` field writes Vault record and stores reference. Reveal disabled by default.

## Choice fields
Static choice row: value + label + optional disabled state.
- duplicate values blocked.
- multi-select default false.
- allow null default true only for optional fields.
- searchable auto-enabled when choice count exceeds UX threshold.
- dynamic choices require Query/Data Source reference and bounded result count.

## Checkbox/true-false
Canonical bool where storage adapter supports; post meta adapter normalizes consistently. UI label semantics must state what true means.

## Date/time
Storage default: normalized machine representation independent of display format.
- date: `YYYY-MM-DD` logical value.
- time: normalized time value.
- datetime: timezone-aware contract; store UTC timestamp/ISO representation according to adapter and retain timezone semantics where needed.

## Color
Validated CSS color format from approved picker formats; no arbitrary CSS string.

## Image/file/media
- return value default stable attachment ID for local WordPress media.
- allowed types configurable; default image field images only.
- max size optional but cannot exceed server limit.
- dimensions validated after upload for image types.
- multiple only for Gallery/File-multiple type.

## Rich text
Uses supported WordPress editor primitives; sanitize according to actor capability. Do not grant unfiltered HTML through a field merely because UI is rich text.

## Code/JSON
- JSON validates parse/schema if schema configured.
- code fields are display/storage text only; never executed by default.
- language selector affects editor highlighting/validation only.

## Repeater
- min default 0.
- max blank means product-defined safe upper bound, not infinite DOM rendering.
- row IDs stable UUIDs for diff/reorder.
- nested depth limited by schema/runtime policy.

## Group
Single structured namespace; storage adapter may flatten or serialize only according to explicit strategy. Queryability warning if serialized.

## Flexible layouts
- each layout stable key/name.
- allowed min/max layouts.
- row stable ID.
- layout switching cannot silently drop fields without confirmation.

## Relationship/entity
- source required.
- single vs multiple.
- min/max selection.
- query filter optional.
- return canonical entity reference, not arbitrary object serialization.
- bidirectional persistence delegated to Relations Builder.

## Map/location
Provider adapter optional; raw coordinate fields work without paid maps provider. Store normalized lat/lng plus optional address components, never provider response blob as canonical value.

## Computed
Expression engine allowlisted. Dependencies declared, cycles rejected. Persisted computed value default false; runtime calculation default unless indexing/performance requires materialization.

## UI-only fields
Tabs/separators/messages create no storage.

## Storage adapters
- post/term/user/comment meta
- options
- custom table
- registered provider

Each adapter declares queryability, uniqueness, indexing, revision behavior and supported field structures.

## Location rendering
Assets enqueue only on editors/screens where active matching group renders.

## Migration
Changing type/storage has migration preview:
- compatible coercion
- lossy conversion
- impossible conversion
- sample affected records
- background migration when large
- rollback snapshot/version.

## Diagnostics/tests
- duplicate keys
- invalid location matcher
- invalid regex
- nested repeater limits
- media MIME spoof tests
- unauthorized field edit
- migration with existing data
- deleted group retains data
- REST leakage

# 4. Relations Builder — Pro

## Relation definition defaults
- status Draft.
- endpoints required before activation.
- cardinality default many-to-many only if user chooses; wizard asks explicitly, no hidden default in persisted data.
- duplicates forbidden.
- self relation false.
- bidirectional traversal true for WPE relation engine, while labels remain directional.

## Endpoints
Each endpoint defines Data Source + entity subtype + label. Eligible record filter Query optional.

Changing endpoint after links exist is migration-class change and blocked without explicit migration plan.

## Cardinality enforcement
- one-to-one: unique both endpoint columns.
- one-to-many: unique child-side as appropriate.
- many-to-many: composite unique pair unless duplicate links explicitly future-supported.
- min cardinality is validation/workflow policy; database cannot always enforce safely.

## Pivot fields
Uses Custom Fields schema subset compatible with relation pivot table. No nested unbounded repeaters by default. Pivot schema migration follows Custom Tables migration discipline.

## Ordering
Optional integer order per direction. Reorder operations are transactional/batched and audited if ordering is business-significant.

## Delete policies
Default: **detach relation rows when an entity is permanently deleted**, but never cascade-delete the related entity.

Options:
- restrict entity deletion because relation exists;
- detach links;
- custom registered policy.

Cascade entity deletion is excluded from normal v1 UI.

## Admin editing
- panel visibility configurable per endpoint.
- actor must have permission to edit both relation and relevant entity relationship operation.
- selector uses bounded Query.
- bulk attach/detach requires confirmation and background job for large sets.

## Runtime/API
Relation traversal enforces permission on returned entities. A user able to view source entity does not automatically gain view access to hidden target entity.

## Integrity diagnostics
- orphan endpoint IDs
- duplicate pairs
- cardinality violations
- missing source provider
- pivot schema mismatch
- count mismatch/cache stale

## Tests
- each cardinality
- concurrent attach uniqueness
- endpoint delete
- target authorization
- pivot migration
- import UUID remap

# 5. Status Manager — Pro

## Two modes
1. WordPress post-status registration/availability.
2. WPEssential domain state machines.

They share UI patterns but not storage semantics.

## WordPress status identity
- key follows current WordPress constraints and collision checks.
- label required.
- label count generated unless overridden with valid singular/plural format.

## WordPress flags
For custom public editorial status, defaults are not guessed from one checkbox; creation wizard asks a preset:
- Public workflow status
- Private/protected status
- Internal status
- Advanced custom

Preset expands to explicit flags before Publish.

Fields:
- public
- internal
- protected
- private
- publicly queryable
- show in admin all list
- show in admin status list

Mutually contradictory combinations are warned/blocked according to WordPress semantics.

## Post-type availability
Explicit multi-select. Empty means status registered but not offered by WPE editor integrations. Third-party editor compatibility shown separately.

## Domain state
- key/name required.
- initial state: at most one per machine.
- terminal: false default.
- color/icon presentation only.

## State machine
- scope required: form entry, support ticket, custom table/entity, workflow object or registered adapter.
- unknown external states preserved read-only where adapter requires.

## Transition
Required:
- from set
- to state
- capability/policy

Optional:
- condition rules
- required fields
- reason required
- confirmation
- workflow before/after
- notification.

Default transition is manual, no side effect.

## Automatic transition
Only via Workflow/Job engine, never a hidden Status cron subsystem.

## History
Append-only status history with actor/source/reason/correlation. Admin corrections create corrective entry; do not rewrite history silently.

## Tests
- impossible transition
- role denied
- condition failure
- external unknown status preserved
- WordPress editor compatibility
- transition side-effect failure handling
