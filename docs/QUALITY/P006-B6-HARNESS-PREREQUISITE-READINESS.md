## 2. Current exact-main facts

### Migration marker sequencing

`MigrationRunner::runPending()` performs, in order:

1. read applied IDs;
2. skip already-applied IDs;
3. safety-check the migration;
4. call `MigrationInterface::apply()`;
5. call `MigrationStateStoreInterface::markApplied()`;
6. append the ID to the current run result.

Therefore a deterministic `markApplied()` failure can occur **after** the migration data/schema step has committed.

The state-store contract is deliberately small:

- `appliedIds(): array`;
- `markApplied(string $id): void`.

That makes a test-only fail-once decorator possible without changing product bootstrap DI.

`WpdbMigrationStateStore` verifies persistence after `INSERT IGNORE` and throws the fixed message `Migration state could not be persisted.` when the marker cannot be read back.

### Current idempotent migration subject

The accepted Pro migrations exercised by Wave 1T are non-destructive `CREATE TABLE IF NOT EXISTS` migrations:

- `220.custom_tables_migration_runs_v1`;
- `221.custom_tables_migration_execution_confirmations_v1`.

Wave 1T already proved their normal compatible admission and exact order. B6 does not reuse that PASS as FP-86 execution.

### Platform API preflight

`LocalCompatibilityPreflight` evaluates Free/Pro marketing-version compatibility before Platform API compatibility.

With the marketing versions held at the exact compatible boundary, a Pro profile whose min/max Platform API is above Free's current `0.1.0` deterministically reaches:

- state: `platform_api_too_old`;
- dimension: `platform_api`;
- premium boot: false;
- premium migrations: false.

Existing unit coverage already proves the pure decision function. A later prerequisite needs a deterministic packaged candidate identity so a formal runtime fixture is not masked by a marketing-version mismatch.

### Backup/restore boundary

`docs/MODULES/BACKUP-RESTORE-SEMANTICS.md` remains explicit planning truth: no product archive creation, DB dump/import, restore runner or destructive restore implementation is authorized.

That does not prevent a **CI-only disposable MySQL snapshot fixture** from preparing an older database state for P-006 evidence, provided it is clearly test infrastructure, never production-facing product behavior, and never marketed or recorded as Backup/Restore product certification.

### Migration-adjacent status/error surfaces

Current generic migration code has no dedicated persistent migration logger.

Relevant emitted/observable surfaces are bounded to:

- `MigrationRunner::runPending()` returned applied-ID list;
- thrown exception messages from migration classes and the state store;
- WordPress/PHP stderr/error-log capture only if the test environment enables it;
- P-006 harness evidence JSON generated by the evidence tooling itself.

Current migration exception strings contain migration/store identifiers or fixed failure descriptions; they do not intentionally serialize DB rows, option values, Vault plaintext, license tokens or arbitrary request/user data.

`SensitiveValue` independently redacts both `__debugInfo()` and JSON serialization to `[REDACTED]`.

## 4. Minimal prerequisite implementations

### B6a — FP-86 fail-once marker-store harness

Allowed future prerequisite files should be evidence/test tooling only.

Required behavior:

1. use a disposable MySQL database and a dedicated prefix;
2. instantiate the real current migration class under test;
3. wrap the real `WpdbMigrationStateStore` with a test-only `MigrationStateStoreInterface` decorator;
4. delegate `appliedIds()`;
5. on the first target `markApplied()`, throw a fixed test-only exception **without** persisting the marker;
6. prove the physical migration effect exists after the failed run while the marker does not;
7. create a fresh runner/request with the normal real state store;
8. prove the exact current idempotent migration safely converges and the marker is persisted once;
9. record that this proves only the exact fixed migration subject, not generic interruption recovery.

Stop if the selected migration becomes destructive, ceases to be demonstrably idempotent, or requires product bootstrap mutation.

### B6b — FP-89 isolated Platform API candidate

Build from the accepted canonical F0/P0 pair.

Test-only P-API node:

- Pro marketing version unchanged;
- min/max Free marketing version unchanged;
- Pro schema bounds unchanged;
- only `WPE_PRO_MIN_PLATFORM_API_VERSION` and `WPE_PRO_MAX_PLATFORM_API_VERSION` become `0.2.0`;
- only `wpessential-pro/wpessential-pro.php` may differ from canonical P0;
- expected state with F0: `platform_api_too_old`;
- expected premium boot/migrations: false.

The prerequisite must derive the candidate twice byte-identically and record ZIP SHA-256, payload-tree SHA-256, changed-entry set and pair ID.

Stop if any marketing-version or schema dimension changes.

### B6c — FP-90 disposable older-DB snapshot primitive

This is test infrastructure only.

Required shape:

1. create a disposable WordPress/MySQL database at a pinned older accepted migration state;
2. export only that disposable DB using deterministic CI tooling available in the MySQL service;
3. hash the SQL snapshot artifact;
4. destroy/recreate the disposable database;
5. import the same snapshot;
6. verify table prefix, migration IDs and normalized WPE schema fingerprint equal the pre-export older state;
7. install/boot the newer exact candidate only after local package compatibility has passed;
8. future formal FP-90 execution may then observe the supported pending migration path.

The prerequisite itself must stop before counting FP-90 and must not be called product Backup/Restore.

Stop if the harness requires live data, credentials outside disposable CI, filesystem restore, product restore code or an irreversible migration.
